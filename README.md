# 存储周期温度计 v3

DRAM/NAND 周期监测。每周一北京时间 08:30 自动运行：Claude 联网**只提取原始指标**，
分数由 `scripts/scoring.py` 机械映射，上传微信云开发 Storage，小程序读取展示。

## v3 与旧版的根本区别

旧版让模型直接打分（0–100 自由裁量）；v3 让模型只填 `wow_pct`、`yoy_pct`、
`inventory_weeks` 等可核对的数值，**打分完全由代码完成**。同一周的实测差异：
旧口径 58 分，新口径 32 分——旧版把 TrendForce 的谨慎措辞（"成交清淡""买方抵制"）
读成了看跌，而同期现货价两周涨了 10.6%、连创新高。

## 输出的四个维度

| 维度 | 含义 |
|---|---|
| 行业温度 | 五信号加权合成分，距周期顶部的接近程度（慢变量已衰减）。页面标题位只显示这一个数 |
| 主触发器 | ①≥38 且 ②≥55 且 ④≥35，回测两轮各提前 2 季度、零误报 |
| 市场定价锚 | DRAM 市场价格指标距高点回撤，独立告警不入分（数据源见 `fetcher.fetch_equity`）|
| 触底信号 | 反转条件凑齐了多少（用变化率构造，≥60 为条件凑齐）。原名「底部温度」，见下节 |

相位状态机（扩张/顶部预警/下行/筑底）确保同样的高分在过顶后含义反转——
36° 在「扩张期」是往上爬，在「筑底期」是已跌透，数字相同含义相反。这也是为什么
标题位可以只留一个数：方向由相位标签承担，不必再并排放第二个温度。

温度的实际取值范围是 **21–62** 而非 0–100（两轮周期峰值 61/62、谷值 21），
故页面标出历史区间尺；`compose()` 的顶部阈值也据此从 70 下调到 60——原值在
35 期回测中从未触及，那条分支是死代码。

**温度峰值滞后实际周期顶部 1–2 个季度**（2018 顶在 Q3、温度峰在 Q4；2022 顶在
Q1–Q2、温度峰在 Q2–Q3）。它是状态描述，提前量在主触发器那里。

## 数据分层（重要）

- `quarterly`：2018Q1–2026Q3 共 35 期，**季度规则重建，非实测**。周度历史数据在付费墙后，
  不做即为不编。置信度逐期标注。
- `weekly`：2026-07 起，**真实现货价实测**，来源 TrendForce 周报（免费公开部分）。

两条序列口径相同、数据性质不同，小程序分 tab 展示，不合成一条曲线。

## 部署

Secrets：`TCB_SECRET_ID`、`TCB_SECRET_KEY`；`TCB_ENV`（仅云开发后端需要）；
`ANTHROPIC_API_KEY`（可选，只影响一句话点评）。
Variables：`COS_BUCKET`、`COS_REGION`（COS 后端）、`ANTHROPIC_BASE_URL`、`CLAUDE_MODEL`。
小程序端只需在 `config.js` 填 `dataUrl`，并把该域名加入 request 合法域名。

### 数据托管：两种后端

GitHub 只负责算，算完的 `data.json` 需要一个**已 ICP 备案的 HTTPS 域名**才能被小程序
`wx.request` 读取——这是微信对服务器域名的硬性要求，GitHub Pages / jsDelivr 一律用不了。
腾讯自有域名天然满足，故有两条路：

| 后端 | 触发条件 | 域名形态 | 风险 |
|---|---|---|---|
| 云开发 Storage | 不设 `COS_BUCKET`，用 `TCB_ENV` | `xxx.tcb.qcloud.la` | 套餐到期/欠费 → 环境停服，整站返回 418 |
| 普通 COS 桶 | 设 `COS_BUCKET` | `桶名.cos.<region>.myqcloud.com` | 与云开发计费解耦；每月成本约 ¥0.01 |

`COS_BUCKET` 一经设置即优先，代码无需改动。负载实况：单文件 14.8 KB（gzip 3.2 KB），
每周写一次，读取量等于小程序访问量——任何计费档下都是零头。

### 为什么小程序端读的是「地址列表」而不是单个地址

`config.js` 导出的是 `dataUrls` 数组，`index.js` 按顺序尝试，第一个成功的即采用
（主源正常时不会多发请求，失败才降级）。这么做是因为微信有两条不对称的规则：

- 改代码包里的地址 → 必须重新上传发布，**要过审核**
- 改后台的 request 合法域名 → **不需要审核**，即时生效，每月限 5 次

把候选地址预先写进代码包，换主机就只剩后台操作，代码包一行不用动，也就不必再提审。
顺带一提，这里触发的是**审核**（免费的版本例行审查），不是**认证**（主体资质），
两者无关，改数据地址不会引发重新认证。

COS 的访问域名可以提前算出来：`{桶名}-{APPID}.cos.{地域}.myqcloud.com`，
APPID 就是现有云开发地址尾段那串数字。所以桶还没建，地址就能先埋进包里。

### 从云开发迁到 COS

顺序很重要——先把后端备好再发版，避免上线当天走降级：

1. 腾讯云控制台建桶，桶名与地域必须和 `config.js` 里预埋的地址一致
   （当前预埋：`thermometer` / `ap-shanghai`），权限设为**公有读、私有写**。
2. 仓库 Variables 加 `COS_BUCKET=thermometer-<APPID>`、`COS_REGION=ap-shanghai`。
3. 手动跑一次 workflow，确认"上传到对象存储"步骤打印的 URL 与预埋地址一致。
4. 小程序后台把 COS 域名加进 request 合法域名（云开发域名先保留，两个并存）。
5. 上传代码包、提交审核、发布。
6. 观察一两周，确认走的是 COS，再退订云开发个人版套餐。
   退订后云开发地址返回 418，会被自动跳过，不需要再改代码。

`TCB_SECRET_ID/KEY` 这对密钥两种后端通用，不必重配。

### 成本

环境到期时间变更为上线后第 15 天**，且不支持按量付费；能长期用的最低档是个人版
¥19.9/月（¥238.8/年）。COS 按量计费：标准存储约 ¥0.136/GB/月、外网下行 ¥0.5/GB。
本项目单文件 14.8 KB、每周写一次，月访问一万次的流量费约 ¥0.07——**每年一两毛钱**。

### 为什么计算与上传是分开的两步

`update.py` 支持 `--dry-run` / `--no-upload` / `--upload-only`（`--help` 见文件末 USAGE）。
workflow 的顺序是**先落盘、先提交、后上传**，且两步互不阻塞：

- 上传原本是 `main()` 的最后一步，存储一旦不可用就会让整个 job 失败、
  `git commit` 根本轮不到执行，当周读数就此蒸发。故把提交挪到上传之前。
- 但只调顺序又会反过来：提交失败（推送被拒、远端跑在前面、对旧 run 做 re-run）
  会让上传步骤被跳过，数据到不了用户手里。故上传步骤带
  `if: always() && steps.compute.outcome == 'success' && steps.selfcheck.outcome == 'success'`
  ——只要读数算出来了且自检通过就必须传，与提交成败无关。
- 提交步骤自己 `git pull --rebase` 后再推，容忍远端已被推进的情况。

自检失败（打分口径漂移或分档表与实际打分对不上）则两步都不做——那种情况下
算出来的东西本身就不可信，不该发出去。

## 「触底信号」为什么不是温度的另一端

原名「底部温度」。两个读数都叫「温度」，读者必然当成同一根尺子的两端，
反复引发「41 和 7 哪个才是真温度」的误读。故更名为**触底信号**——
JSON 字段名仍是 `bottom`，只改展示名，线上旧版本代码包不受影响。

两者回答的是**不同的问题**：

| | 问的是 | 怎么算 |
|---|---|---|
| 行业温度 | 顶部特征积累到什么程度了——**危不危险** | 五信号加权的**水平值** |
| 触底信号 | 反转条件凑齐了没有——**能不能主动买** | 四个分项的**变化率** |

必须用变化率，是因为周期底部的特征**不是**「库存高」——那是下行期的特征——
而是「库存正在去化、价格正在企稳、供给已经投降」。水平值看不出这个。

四个分项：供给投降 30%、库存去化 25%、价格企稳 25%、悲观一致 20%。
小程序里可点开看各分项当期得分，加权后能精确还原总分。

最能说明问题的一对：

| 期 | 行业温度 | 触底信号 | 相位 |
|---|---|---|---|
| 2018Q1 | **36°** | 18 | 扩张期 |
| 2019Q4 | **36°** | 99 | 筑底期 |

温度一模一样，一个是上行刚起步、一个是周期最底部。**温度分不开的，这个数分得开**——
这就是它不能被删掉、也不该被并成一个数的原因。

低于 60 不代表危险，只代表「还不是主动买入的时点」。

## 对外文案的口径

2026-08-21 首次提审被拒，理由是「存在个人主体小程序未开放的服务类目」（金融相关）。
据此把对外呈现的证券语汇改写为产业语汇：

| 原文案 | 改为 |
|---|---|
| 市场定价锚 · DRAM **ETF** | 市场定价锚 · DRAM |
| **股价**已深度回撤 | **资本市场**已深度回撤 |
| **卖方**一致性与话术 | **行业预期**一致性 |
| **看空** N 方 | **异议** N 方 |
| 应制定**退出触发条件** | 供需矛盾持续积累，历史上距周期转折约 6–12 个月 |
| 还不是**主动买入的时点** | 产业尚未出现触底特征，与景气好坏无关 |
| 不是**择时信号** | 描述产业当前所处的位置，而非对未来的预判 |

**内部代码注释与数据源说明一律保持原样**——`fetcher.fetch_equity` 的 docstring
仍写明数据来自 Roundhill Memory ETF (DRAM)，`scoring.py` 里关于美光股价领先性的
回测注记也原样保留。对外用什么措辞是产品决定，代码必须如实记录数据到底是什么，
否则维护者会被自己的文案误导。

底部声明同步改写，且**必须与页面实际一致**：定价锚数据仍在展示，声明里就不能写
「不展示证券行情」，只能写它的真实用途——「引用公开市场价格指标，仅作为产业周期的
旁证，不作个股或产品指向」。声明与内容自相矛盾比没有声明更糟。

## 信号①的口径说明

信号①原名「现货价 vs 合约价」，但**合约价没有公开数据源**——`premium_pct` 一直是
`update.py` 里写死的假设值 120%，从未参与实际判档（它落在 `p>=20` 分档，只要现货在涨
分数恒为 10，这就是历史上该信号每期都是 10 的原因）。故更名为「现货价动能」，
实际判据只有周环比与连跌期数，图表也只画现货一条线。这一点在小程序的展开说明里如实写出。

## 打分逻辑的展开说明

每个信号卡可点开，展示统计范围、完整分档表、本期命中哪一档、离下一档还差多少、
以及它在主触发器中的角色。**说明文本不手写**——分档表写在 `scoring.py` 的
`explain_*` 里，`verify_explain()` 在输入网格上逐点比对表与真实 scorer，
`probe.py` 每次运行都跑这个对账，表一旦与打分漂移立刻报错并阻断发版。

## 小程序端的静态检查

`scripts/check_miniprogram.py` 校验每个展开入口（`class="q"` 的文字）都处在带
`bindtap` 的元素之内。上线过一次这样的 bug：「打分逻辑 ›」写在 `.met` 里，而
`bindtap` 绑在兄弟元素 `.sig-head` 上，点了没反应——而单测直接调 `toggle()`，
绕开了绑定，测不出来。上传代码包前跑一次。

## 口径一致性保障

1. 打分规则集中在 `scoring.py`，实时与回测**共用同一份代码**，不可能出现两套口径。
2. workflow 每次运行后自动跑 `backtest/probe.py` 回归自检，规则被改动导致历史结论变化会立刻暴露。
3. 季度类指标带 `asof` 发布日，未更新则沿用上期数值，杜绝无信息期的虚假微调。
4. `history_v3.json` 随 git 提交，每期读数的指标、来源、置信度可追溯。
